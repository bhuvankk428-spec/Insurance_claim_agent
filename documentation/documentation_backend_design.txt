Backend System Design
=====================

Purpose
-------
Backend is split into two independent services:
1. Chat service (RAG)
2. Claimcheck service (claim verification + admin + finance news proxy)

This separation allows independent scaling and fault isolation.

Architecture
------------
- Frontend calls same-origin `/api/*` routes. Locally the Vite proxy splits traffic: `/api/rag-chat` -> chat service, other `/api/*` -> claimcheck service.
- In production, `api/*.js` Vercel entrypoints re-export the chat and claimcheck apps.
- Both services load environment variables and enforce startup checks.
- Both services apply CORS from `CORS_ORIGIN`.
- Finance news is fetched server-side by claimcheck (`/api/finance-news`) and returned to frontend.

CORS Model
----------
- `CORS_ORIGIN` accepts comma-separated origins.
- Explicit and wildcard patterns are supported (example: `https://*.vercel.app`).
- Missing/mismatched origin returns CORS rejection.

Chat Service Design (`backend/chat`)
------------------------------------
Flow:
1. Validate `POST /api/rag-chat` request
2. Retrieve candidate chunks from Postgres (embedding similarity)
3. Rank candidates
4. Stream OpenAI output tokens to client

Chunk index pipeline:
- `scripts/buildChunks.js` derives one chunk per leaf value from `data/*.json`.
- Short enum/boolean/number/list leaves are rendered as full sentences (for
  example `coverage.hospitalization: hospitalization is covered`), so
  answer-bearing fields (room-rent cap, maternity, premium structure, claim
  trigger) are not dropped or indexed as bare tokens. Rendering is keyed by
  value type, not only by length, so long snake_case enums are still rendered.
  `false`/`0` are preserved.
- `scripts/embedChunks.js` embeds the chunk file into `policy_chunks`. The seed
  step and `retrieval.js` queries must use the same provider/model/dimension;
  otherwise pgvector ranking is meaningless even when the expected chunk exists.
- Clear `policy_chunks` before a full re-seed because the embed script appends.

Note:
- `POST /api/finance-podcast` exists in chat service, while the frontend route `/ai-finance-podcast` is currently a Coming Soon placeholder.
- The `/finance-podcast` frontend route is a static curated list and makes no backend call.

Startup constraints:
- Requires DB readiness when `REQUIRE_DB_READY=true`.
- Fails fast if `DATABASE_URL` is missing in enforced mode.

Claimcheck Service Design (`backend/claimcheck`)
------------------------------------------------
Flow:
1. `POST /api/claim-check` validates policy and creates claim session
2. `POST /api/claim-evidence` processes FIR + photos and match rules
3. Frontend stores returned `claimContext` in browser session storage
4. `POST /api/claim-story` evaluates narrative + coverage and persists decision
5. Story step can restore missing in-memory session state from `claimContext` on serverless/production requests
6. `GET /api/my-claims` returns claim history for the signed-in user dashboard
7. Admin routes read/update persisted decisions in Supabase
8. Finance route fetches latest market headlines for frontend cards

Decision safety notes:
- If OpenAI is unavailable or returns invalid story JSON, the story step falls back to partial approval/manual review (no auto-approve fallback).
- Geo signal uses a fallback chain:
  1) EXIF GPS metadata from uploaded image
  2) OCR-based coordinate parsing from visible image text/watermark
  3) OpenAI vision coordinate parsing from visible image text/watermark (when `OPENAI_API_KEY` is configured)

Startup constraints:
- In production, `ADMIN_TOKEN` must be set and non-default.
- Supabase readiness can be enforced with `REQUIRE_SUPABASE_READY=true`.

State and Durability
--------------------
- In-progress claim session data is built in-memory (`claimStore`) and mirrored to the frontend as serialized `claimContext`.
- Final claim records are stored in Supabase.
- Restarting claim service clears in-memory sessions, but the story step can rebuild the required context from the browser-provided `claimContext`.
- In-progress claim durability is browser-session scoped, not fully database-backed.

Model Quality Evaluation
------------------------
- `eval/` is a non-production harness. It does not change runtime behavior.
- Claim/image evaluation calls the real service functions with fixed contexts.
- RAG evaluation can use live pgvector (`db`), local embeddings over the chunk
  file (`embed`), or the production keyword fallback (`keyword`).
- Results include accuracy, invalid/repair JSON rates, latency, and token cost.
- Reports are written to `eval/results/`; `eval/compare.js` compares two runs.
- AI telemetry is recorded by `backend/claimcheck/utils/aiTelemetry.js`.

Operational Notes
-----------------
- Frontend and backend are deployed together on Vercel and communicate over same-origin `/api/*`.
- Admin API requires token alignment between frontend and claim backend.
- For local `npm run backend`, set distinct ports (for example `CHAT_PORT=5175` and `CLAIM_PORT=5174`).
- If startup fails with `EADDRINUSE`, stop the stale process using that port or change `CHAT_PORT` / `CLAIM_PORT`.
- Recommended deploy order: chat backend, claim backend, then frontend.
