Backend System Design
=====================

System Design Overview
----------------------
This file focuses on the backend system design for QK.AI.
It explains the overall architecture, data flow, runtime lifecycle, and service boundaries.
The backend is split into two Express services: chat (RAG) and claimcheck (OCR + rules).
Both services load configuration from the root .env to keep deployment centralized.

Chat Backend Design (RAG)
-------------------------
Key goals: low-latency responses, transparent retrieval, and scalable data ingestion.
The chat service exposes a streaming endpoint: POST /api/rag-chat.
Requests include question, optional domain, and optional details.
The pipeline performs retrieval over chunked policy data using embeddings and vector similarity.
Results are scored with rule heuristics and passed to the LLM for final synthesis.
Tokens are streamed to the client to improve perceived performance.

Claimcheck Backend Design
-------------------------
Key goals: accurate OCR, consistent extraction, and reliable claim decisions.
The service exposes /api routes for claim creation and validation.
Documents are parsed via OCR (Tesseract) and normalized into structured fields.
Matching logic aligns extracted fields with policy and evidence rules.
Decisions are persisted to Supabase for retrieval by the frontend.

Operational Concerns
--------------------
CORS is configured per service and can be tightened for production.
Chat service depends on Postgres + pgvector and a local LLM runtime (Ollama).
Claimcheck depends on OCR data files and external APIs (Groq, Supabase).
The monorepo uses a concurrent script to launch both services locally.
